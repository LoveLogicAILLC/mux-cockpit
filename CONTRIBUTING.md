# Contributing to mux-cockpit

Thanks for looking at this. It's a young project (see the state below) — issues, PRs, and
questions are all welcome, but expect the process to be manual and the bar for review to be
"a human actually read your diff," not a green CI badge.

## Dev environment

Requirements:
- Python 3.10+ (`run.sh` and `build.sh` both hard-check this at startup)
- Go 1.22+ (`go.mod` pins `go 1.22`)
- [Ollama](https://ollama.com) if you want to test the `ollama` provider or run fully offline
  (optional — the `mock` provider needs nothing)

Clone, then:

```bash
bash build.sh
```

This runs `go mod tidy`, `go vet ./...`, and builds `bin/cockpit` (host arch) plus
`bin/cockpit-darwin-arm64` (cross-compiled). No separate Python install step — the host
orchestrator and harness only use the standard library (see `harness/providers.py`'s module
docstring: "Stdlib HTTP only").

To run the whole stack locally against the mock provider (no API keys, no Ollama):

```bash
MUX_PROVIDER=mock bash run.sh
```

or headless, via `make demo`.

## Code style

There's no linter/formatter config in the repo (`make fmt` just runs `gofmt -w *.go` — no
`black`/`ruff`/`isort` for Python). Match what's already there:

- **Terse over verbose.** Functions are short; comments explain *why* a non-obvious decision
  was made (see the `ponytail:` comments in `host_orchestrator.py` for the style — one line
  naming the shortcut taken and the upgrade path, not a paragraph), not what the code
  obviously does.
- **No speculative abstraction.** One provider class per backend, no factory layer beyond
  `make_provider()`'s if/elif chain. No config knobs for values that never change.
- **Stdlib first.** `harness/providers.py` does raw `urllib.request` + a hand-rolled
  thread→asyncio bridge for streaming HTTP rather than pulling in an HTTP client dependency.
  Follow that precedent — don't add a new pip/go dependency for something a few lines of
  stdlib code can do.
- **Real primitives in tests, not mocks of them.** See `docs/TESTING.md` — orchestrator tests
  use real temp-dir git repos and real Unix sockets. Don't introduce a mocking framework.
- Go: standard `gofmt` formatting, run `go vet ./...` before submitting (also part of
  `build.sh` and `make test-go`).
- Python: no type-checker is wired into CI, but the existing code is fully type-hinted where
  it's not obvious from context — match that.

## Running tests before submitting

```bash
make test          # everything
make test-py         # python3 -m unittest discover -s tests -v
make test-go          # go vet ./... && go test ./...
```

All tests must pass with `MUX_PROVIDER` unset or `mock` — nothing in `tests/` should require
a real API key or a running Ollama daemon. If you're adding a provider (see
`docs/PROVIDERS.md`), add wire-format tests against a fake HTTP server the way
`tests/test_harness.py`'s `TestProviders` class does for the existing ones, not against the
live API.

If you touch `host_orchestrator.py`'s retry loop, the workspace lock, or the git commit path,
read `docs/TESTING.md`'s walkthrough of `test_review_rejection_retries_then_archives` and
`test_concurrent_tool_tasks_never_mix_commits` first — those are the two tests most likely to
catch a regression in that area, and if your change legitimately alters that behavior, update
them rather than deleting or loosening the assertions.

## Commit messages

No enforced convention yet, but please use [Conventional Commits](https://www.conventionalcommits.org/)
(`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`) with a short imperative summary
line. Example: `fix: prevent workspace lock deadlock in select_worker fallback`.

Note: `mux:`-prefixed commits (e.g. `mux: <event message>`) are auto-generated by the
orchestrator itself when `MUX_GIT=1` is set (see `HostOrchestrator._git_commit` in
`host_orchestrator.py`) — those are swarm output commits, not something you write by hand.

## Review process

There is no CI pipeline yet — `make test` is run manually by whoever reviews a PR (or by you,
before opening one; do this). Until CI lands, every PR gets a manual read-through rather than
an automated gate, so:

- Keep diffs scoped to one concern; it's easier to review a focused change by hand.
- Call out in the PR description which of `make test-py` / `make test-go` you ran locally and
  that they passed — there's no badge to point to instead.
- If your change affects provider selection, the git integration, or the MUX router's
  concurrency behavior, mention it explicitly — those are the areas with the most subtle
  failure modes in this codebase (see `docs/PROVIDERS.md` and `docs/TESTING.md`).
